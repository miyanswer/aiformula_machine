# web_simulator コース幾何データ化・実寸化と当たり判定 設計書

- 日付: 2026-09-21
- 対象: `web_simulator/`（実機側 `src/`, `launchers/`, `control/` の変更なし）
- 要求: 白線幅 15 cm / 車線幅 3.5 m となるようコースを再設計する。障害物とコース逸脱に当たり判定をつける。

## 背景・現状の計測

現行コースは `png/shihou_cource_unity.png`（1024×819）を 100 m × 80 m の板に貼っただけで、実寸はモデル化されていない（`js/course.js` のコメントに「Real-world scale is not modeled yet」と明記）。白線の位置は `tools/extract_course_lines.py` が画像から放射レイで抽出し、`js/course_lines.js` に 1440 点／線として吐いている。

実測した現状値:

| 項目 | 実測 | 備考 |
|---|---|---|
| 車線幅（外側境界↔中央線） | 平均 3.286 m（p10 3.08 / p90 3.57） | 手描き画像由来で ±0.3 m ばらつく |
| 車線幅（中央線↔内側境界） | 平均 3.268 m（p10 3.03 / p90 3.66） | 同上 |
| 白線幅 | 約 24 cm（テクスチャ上 2.5 px） | 画像解像度 9.77 cm/px |
| 外周ループ中央線の全長 | 237.3 m（生データ） / 231.2 m（平滑化後） | 差分はトレースのジッタ |
| 線幅:車線幅 | 1 : 13 | 目標は 1 : 23（0.15 : 3.5） |

比率が違うため、**PNG を拡大縮小するだけでは 15 cm と 3.5 m を同時に満たせない**。また 15 cm はテクスチャ上 1.5 px にしかならず、機体カメラ（ZED 相当、YOLOP/UFLD の入力）に耐える描画にならない。

なお `js/lane_navigator.js` の `LINE_TRACKER_PARAMS.laneWidthInit` は既に `3.5` であり、コードが想定する車線幅と実際のコース（3.27 m）がずれていた。本件はこのずれの解消でもある。

## 方針

外周ループ（車両が走り、白線検出の対象になる部分）だけを幾何定義から生成し、内側の造作（交差点・横断歩道・駐車枠・芝生島）は PNG のまま実寸に載せる。

## 設計

### 1. 縮尺

`COURSE_WIDTH_M` を 100 → **106.80 m** にする（奥行 85.42 m）。

倍率 k = 3.5 / 3.2772 = 1.0680。3.2772 は外側↔中央と中央↔内側の全サンプルをプールした平均。生成する白線は基準パスから厳密に ±3.5 m に置くので車線幅は縮尺に依らず 3.5 m になるが、**背景 PNG とのズレを最小化する**ためにこの k を選ぶ。

原点は現行のスポーン地点 (0, −1.6) に固定する（オドメトリ原点と HUD 表示の意味を保つため）。テクスチャ板の位置は平行移動のみで追従させる:

```
COURSE_POSE_new = w0 - k * (w0 - COURSE_POSE_old)
                = (0, -1.6) - 1.0680 * ((0, -1.6) - (13.22, 35.41))
                = (14.119, 37.927)
```

`COURSE_POSE.yaw` は π/2 のまま（回転補正はしない。平滑化後の始点接線は約 −0.5° で、回転させるほどの量ではない）。

### 2. 基準パス（中央線）の平滑化

抽出済みの中央線を閉曲線として扱い、FFT ローパスで ±0.3 m のジッタを落とす。

- 欠損（破線の切れ目）はレイ角をパラメータとした周期線形補間で埋める
- rfft → **30 次より上のハーモニクスを 0** → irfft

ハーモニクス数は実測から決めた:

| 次数 | トレースとの RMS 偏差 | 最小曲率半径 |
|---|---|---|
| 15 | 5.3 cm | 13.1 m（コーナーが鈍る） |
| 25 | 3.7 cm | 10.2 m |
| **30** | **3.4 cm** | **10.4 m** |
| 40 | 3.1 cm | 7.8 m（ノイズが乗り始める） |
| 60 | 2.5 cm | 2.9 m（明確にノイズ） |

30 次を既定値とし、ツールがこの表と同じ診断値を毎回出力するので後から調整できるようにする。

### 3. コース幾何定義 `js/course_geometry.js`（新規・生成物）

ビルドツールが生成する。手書きしない。

```js
export const COURSE_GEOMETRY = {
  laneWidthM: 3.5,        // 中央線 <-> 境界線
  lineWidthM: 0.15,       // 白線の幅
  centerPath: [[x, y], ...],   // 平滑化済み基準パス（閉曲線, 等弧長 0.10 m 間隔）
  lengthM: 246.9,              // 基準パス全長（231.2 m × 1.0680）
  startPose: { x: 0, y: -1.6, yaw: -0.009 },  // s=0 の点と接線方位
  dash: { markM: 2.8, gapM: 2.6 },            // 中央線の破線パターン
  innerGaps: [[sStart, sEnd], ...],           // 内側境界線の接続口（下記）
};
```

破線パターンは上側ストレートで実測した mark 2.6 m / gap 2.4 m を k 倍して丸めた値。日本の道路標準（5 m / 5 m）ではなく現状の見た目を保つ側を採った（要求は線幅と車線幅のみのため）。定数なので切り替えは 1 行。

`innerGaps` は内側境界線が内側道路と接続するために開いている箇所。抽出データ上で 1.5 m を超える欠損として現れる区間（現行縮尺での実測は 1.61 / 3.02 / 4.29 m の 3 箇所。ツールが k 倍して格納する）を弧長区間として持ち越す。ここを埋めてしまうと接続口が白線で塞がれてしまう。外側境界線は実質連続（最大欠損 0.32 m ＝抽出のドロップアウト）なので完全な実線として生成する。

基準パスの最小曲率半径 10.4 m に対してオフセット量は 3.5 m なので、オフセット線が自己交差することはない。

### 4. ビルド時ツール `tools/build_course.py`（`extract_course_lines.py` を置き換え）

1. PNG を読み、現行と同じ放射レイで 3 本線を抽出する（既存ロジックを流用）
2. 中央線を平滑化し、等弧長で再サンプルして基準パスにする
3. k を掛けて実寸に載せ、`js/course_geometry.js` を生成
4. 基準パスから ±3.5 m のオフセット線を求め、`js/course_lines.js` を**定義から**生成する（抽出結果ではなくなるので、理想検出モードの座標が描画と完全一致する）

   **破線の切れ目と接続口は `null` として残す。** `js/ideal_lane_detector.js` は `COURSE_LINES` の `null` を「そこに線が無い」として扱い、理想検出モードのリアリティ（破線・合流部では線が見えない）を作っている。定義から連続線を吐くとこの性質が失われ、理想検出が実際より良くなってしまう。生成時に中央線へ `dash` パターンを、内側境界線へ `innerGaps` を適用し、描画されない区間は `null` にする。外側境界線は実線なので `null` なし
5. PNG から外周ループの 3 本線を消した `png/shihou_cource_base.png` を出力。消去方式は「**抽出された**各線の位置（平滑化後の生成位置ではない）を中心に法線方向 **±45 cm** の回廊をとり、その中で**輝度 195 超の画素だけ**をアスファルト色 RGB(156,150,156) に置き換える」。

   - 回廊幅の根拠: 抽出位置は k 倍後に 3.5 m ± 0.32 m でばらつくので、厳密に 3.5 m に置く生成線は抽出位置から最大 0.32 m ずれる。線の半幅 0.075 m を足して 0.395 m < 0.45 m なので、生成線は必ず消去済み領域の中に収まる。
   - 白画素だけを置換するので、回廊内にある白以外の内容（アスファルト、芝生）は影響を受けない。
   - 外側境界線のさらに外側にある二重線（路端の縁石線。抽出ロジックの `runs[0]`）は**残す**。3.5 m の車線の外側にあり、コースの見た目を構成する要素のため。実測では外側境界線から 0.73〜1.20 m（1 パーセンタイル 0.73 m）離れており、±45 cm の回廊には入らない。レイ全体の 0.7% だけ 0.45 m を下回る（抽出のアーティファクト）が、そこは縁石線も一緒に消える。見た目の問題のみで走行・検出には影響しない。

   元 PNG は残す（再生成の入力なので消さない）
6. 診断出力: 平滑化の偏差・最小曲率半径・全長・車線幅の残差。あわせて `simulator.js` にそのまま書き写せる **`COURSE_POSE` の最終値**を出力する（ツールは基準パスをスポーン地点にアンカリングする平行移動を内部でかけるため、仕様書の計算値 (14.119, 37.927) をそのまま使うと背景がずれる）

### 5. 白線の描画（リボンメッシュ）

`js/course.js` に追加。基準パスから ±3.5 m の線を、幅 15 cm の平帯（三角形ストリップ）として `THREE.Mesh` 化し、`rosRoot` の子として z = 0.02 に置く（テクスチャ板の z = 0.01 より上）。

- 外側境界線・内側境界線: 実線（内側は `innerGaps` の区間を飛ばす）
- 中央線: `dash` に従って区切る
- マテリアルは `MeshBasicMaterial`（アンリット）。テクスチャ板と同じ扱いにして、照明条件で白線の見え方が変わらないようにする。色は元 PNG の白線色 RGB(219,212,221)

頂点数は概算で (246.9 m / 0.10 m) × 2 本 × 2 頂点 + 破線分 ≈ 1.2 万頂点。実線 2 本で約 1 万、破線はその半分以下。

### 6. 当たり判定 — 障害物（物理的に阻止）

`js/collision.js`（新規）に 2D 円同士の判定を置く。

**障害物側**: `js/course_props.js` が衝突円のリストを明示的に持つ。`MyLaps.obj` のグループ名から自動抽出はしない（モデル差し替えで壊れるため）。モデルローカル座標（m、`MYLAPS_POSE` 基準）:

| 部位 | 中心 (model x, y) | 半径 |
|---|---|---|
| 支柱 L / R | (∓0.23, −0.032) | 0.019 m |
| コーン 1/2/3 | (−0.31, 0.55) / (0, 0.55) / (0.31, 0.55) | 0.15 m |

**車両側**: base_link 基準に 2 円のカプセル近似。中心 x = +0.30 と x = −0.50、半径 0.40 m（`RACELINE_PARAMS.vehicleHalfWidth` と同値）。全長約 1.6 m ×幅 0.8 m を覆う。

**応答**: `VehiclePhysics.step()` / `stepAutonomous()` の**後**に位置補正として適用し、物理モデル自体には手を入れない。各車両円と各障害物円について:

```
n = normalize(車両円中心 - 障害物中心)      // 障害物から離れる向き
penetration = (rVehicle + rObstacle) - 距離
if penetration > 0:
    車両位置 += n * penetration              // 貫入を押し戻す
    if dot(車両前方ベクトル, n) < -0.5 and v > 0:
        v = 0                                // ほぼ正対 -> 停止
```

`VehiclePhysics` の速度は進行方向スカラー `v` のみ（`vx`/`vy` を持たない差動二輪モデル）なので、法線／接線への速度分解はそのままでは意味を持たない。位置補正だけで「前進分のうち法線成分が打ち消され、接線成分だけ残る」＝障害物に沿って滑る挙動になるため、速度側は正対時の停止だけを扱う。

### 7. 当たり判定 — コース逸脱（警告のみ）

基準パス上の最近傍点を求め、横方向符号付き距離 `offset` を出す。判定式:

```
|offset| > laneWidthM + lineWidthM / 2 - vehicleHalfWidth
         = 3.5 + 0.075 - 0.40 = 3.175 m
```

＝車体の一部が境界線の外縁を越えたら逸脱。走行は止めない。

- HUD に逸脱中の警告表示と累計回数を出す
- チャタリング防止に履歴を持ち、`|offset| < 3.0 m` に戻るまで次の 1 回を数えない
- ROS トピックは発行しない（実機側に対応するノード・トピックが存在しないため、実機と乖離した偽のトピックを作らない）

最近傍点探索は毎フレーム全点走査せず、前フレームのインデックス近傍だけを見る（閉曲線なので前後 ±40 点で十分）。

### 9. 検証方針

このプロジェクトには JS のテスト基盤がないため、ブラウザ上のスクリプト検証で確認する（`mcp__Claude_Browser__javascript_tool` でページ内の値を直接読む方式。本セッションで既に色の不具合特定に使って機能している）。

1. **寸法**: `COURSE_GEOMETRY` から生成した 3 本線について、基準パス各点での外側↔中央・中央↔内側距離が 3.5 m ± 1 mm であること。白線リボンの幅が 0.15 m ± 1 mm であること
2. **背景との整合**: 生成した外側境界線・内側境界線が `shihou_cource_base.png` の塗り潰し帯の内側に収まり、はみ出しが無いこと（スクリーンショットで目視 + 塗り残しピクセル数を計測）
3. **スポーン**: 起動直後の車両位置と中央線の距離が 5 cm 未満であること
4. **理想検出との一致**: `IdealLaneDetector` が返す中央線の横位置と、幾何定義から計算した横位置の差が 1 cm 未満であること
5. **障害物衝突**: ゲート正面から前進させ、支柱／コーンにめり込まず停止または滑ること。貫入量が常に 1 mm 未満であること
6. **逸脱判定**: 車両を横方向に段階的にずらし、3.175 m を跨いだ瞬間にカウンタが 1 増え、3.0 m 未満に戻るまで増えないこと
7. **自動運転**: MyLaps ゲートを一時的に非表示・衝突無効にした状態で、マッピング 1 周 → レースラインで 1 周が従来どおり完走すること（縮尺変更でナビゲータのパラメータ再調整が要るかの確認）
8. **障害物での停止**: ゲートを有効に戻し、自動運転がゲート手前で停止すること（将来の YOLO コーン回避の出発点となる挙動）

## 非スコープ

- 内側道路・交差点・横断歩道・駐車枠の実寸化（PNG のまま。外周ループと同じ k で拡大されるので相対関係は保たれるが、それぞれが厳密に 3.5 m / 15 cm である保証はない）
- コースレイアウト自体の変更（四方コースの形は維持する）
- 中央線の踏み越え（反対車線へのはみ出し）判定
- 衝突・逸脱の ROS トピック化
- MyLaps ゲートの寸法変更・移設（下の「決定事項」のとおり、通過不能なまま据え置く）
- コーン検知 YOLO と回避行動（今回の当たり判定はその前提条件を作るところまで）

## 決定事項: MyLaps ゲートは通過不能のままにする

当たり判定を入れると、中央線上のゲートは支柱間 0.46 m ＜車両幅 0.8 m なので物理的に通過不能になり、現状の自動運転（`LaneNavigator`）は必ずそこで停止する。

**これを許容する。** 理由は、今後コーン検知の YOLO を導入して回避行動を取らせる予定であり、そのときに「避けなければ通れない障害物」がコース上にあることが前提条件になるため。`MYLAPS_SCALE` の拡大・路肩への移設・衝突対象からの除外はいずれも行わない。

この決定の帰結として、検証項目 7（自動運転の周回）は**ゲートを非表示にした状態で行う**。そのために `window.__sim` のデバッグオブジェクトにプロップのルートと衝突円リストを露出させ、検証スクリプトから一時的に無効化できるようにする（本セッションで色の不具合特定に使ったのと同じ経路）。ゲートを有効にしたままの周回は、ゲート手前で停止することが期待挙動であり、失敗ではない。
